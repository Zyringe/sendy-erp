## รูปแบบสคริปต์ (ตาม `.claude/rules/verification-discipline.md`)

`BEGIN IMMEDIATE` → แก้ → **assert ทุกข้อในทรานแซกชัน** → พังข้อไหน rollback ทั้งชุด
→ ค่อย `commit` → เปิด connection ใหม่อ่านซ้ำเป็นสัญญาณอิสระ
ไม่มี flag `rehearse|live` หลอกๆ — path ของ DB คือโหมด

fingerprint (sha256 ของทุกแถว) ของ `salary_advances`, `payroll_items` และคอลัมน์เงิน/
วัน/บัญชี/แท็ก ของ `cashbook_transactions` ถูกเทียบ *ในทรานแซกชัน* ก่อน commit
ถ้าอะไรที่ห้ามแตะขยับแม้แถวเดียว → rollback

## รอบแก้ตาม /scrutinize — `fix_from_account_id.py` (ทำแล้วเช่นกัน)

`apply_round2_links.py` ผูก FK ฝั่ง cashbook แต่ปล่อย `salary_advances.from_account_id`
ว่างไว้ทั้ง 16 แถว ทั้งที่ writer ของแอปเองใส่ค่านี้ใน INSERT เดียวกับที่สร้างลิงก์
(`blueprints/cashbook.py:1037-1043`) — **ผูกคู่ไว้ครึ่งเดียว**

สาเหตุ: สคริปต์รอบ 2 assert ว่า fingerprint ของ `salary_advances` **ห้ามเปลี่ยน**
ข้อจำกัดที่ตั้งเอง แล้วมันบล็อกคอลัมน์เดียวที่*เป็นส่วนหนึ่งของการผูกคู่*

แก้แล้ว: 16 แถว → `from_account_id` = `account_id` ของแถวเงินสดที่ผูกอยู่
(15 แถว → บัญชี 1 `392`, ct 642 → บัญชี 5 `กิติยา`) ผลรวม 28 คู่: 392 = 25, กิติยา = 3
`from_account_id IS NULL` เหลือ **0** · ไม่แตะคอลัมน์เงินและไม่แตะ `cashbook_transactions`

สคริปต์นี้ปิดรูของรอบ 2 ไปด้วย 2 อย่าง: **เปิด `PRAGMA foreign_keys=ON`**
(รอบ 2 เขียนคอลัมน์ FK โดย enforcement ปิดอยู่ — `sqlite3.connect()` default OFF
ส่วนแอปเปิดใน `get_connection` — ตรวจเองล้วน DB ไม่ได้หนุนหลัง) และ
**assert `direction = 'expense'`** (รอบ 2 ไม่ได้ตรวจ ทั้ง 16 เป็น expense จริงแต่นั่นคือโชค)

ซ้อม 4 ด่านบน snapshot: apply สะอาด · รันซ้ำแล้วปฏิเสธ · ทำ ct 642 เป็น income
แล้ว rollback คืนไฟล์เหมือนเดิม · ชี้บัญชี 9999 ที่ไม่มีจริงแล้วถูกปฏิเสธ (พิสูจน์ FK เปิดจริง)
