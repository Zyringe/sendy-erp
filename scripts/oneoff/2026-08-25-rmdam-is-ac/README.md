**ทำไปแล้วทั้ง prod และ local เรียบร้อย ไม่ต้องรันซ้ำ.** ทั้งสองไฟล์เก็บเป็น *หลักฐาน*
ไม่ใช่เครื่องมือ — นามสกุล `.py.txt` เพื่อไม่ให้ใครเผลอรัน (ถ้ารันจริงมันจะปฏิเสธเองที่

**รมดำ = ผิวรมดำ (color code AC) ไม่ใช่สีดำ (BLK)** รอบ backfill `2026-04-17 10:48:19`
(82 ตัว) อ่านคำว่า "รมดำ" เป็นสีดำ แล้วสร้างสินค้าใหม่แทนที่จะจับคู่กับ 559 ที่มีอยู่แล้ว

## หลักฐานที่เก็บระหว่างทาง

- **break-it-once 4 ทาง แดงด้วยเหตุผลที่ถูกต้อง + control เขียวทุกครั้ง**
  ถอดขั้นล้างยอดยกมา → `559 stock is 24, expected 0` ·
  แกล้งข้าม `unit_conversions` → count assert จับได้ ·
  ถอดการเปลี่ยนสี → builder คืนชื่อ BLK ·
  แก้ชื่อด้วยมือใน DB → precondition "builder ต้อง reproduce ชื่อที่เก็บอยู่" ปฏิเสธ
- **row-diff**: 31 ตาราง เปลี่ยนนอกสองสินค้านี้ **0 ตาราง** และมี control (แกล้งแก้
  `product_locations` ของ pid 560) พิสูจน์ว่าการตรวจนี้จับแถวแปลกปลอมได้จริง
- **prod ↔ local ตรงกันระดับค่า** (sha256 ของแถว) ไม่ใช่แค่นับแถว
- **sweep ปิดเคส**: detector "สินค้าจาก batch ที่ไม่มี family แต่แชร์ชื่อ BSN กับพี่น้อง
  ที่มี family" → **0 กลุ่มบน DB ปัจจุบัน** และ **control บน snapshot ก่อนแก้จับ pid 1880
  ได้ 1 กลุ่มพอดี** → ไม่มีเคสแบบนี้เหลืออีกในทั้ง batch `2026-04-06` และ `2026-04-17`
- ไฟล์ pre-state ของ 6 ตารางที่**ไม่มี audit trigger** (`unit_conversions`,
  `product_code_mapping`, `stock_levels`, `product_cost_ledger`, `product_price_history`,
  `product_locations`) → `data/exports/merge_1880_to_559_PROD_prestate_20260825.json`
  (gitignored) · `audit_log` เก็บเฉพาะ `transactions` / `sales_transactions` /
  `purchase_transactions` / `products` / `product_price_tiers` เท่านั้น **จึง rollback
  จาก audit_log อย่างเดียวไม่ได้**
